# Webアプリ・ESP連携：既存仕様での接続・試験方針

更新日：2026-11-11

いただいた資料のマイコン仕様に合わせて、まずこちらのアプリ側を実装しました。
会話・BGM・予告音・実機のパリィ・弱点Aまでつないで試し、音と判定のずれが実際にどれくらい問題になるか確認したいです。

前案にあったJSON化、チャンスIDの追加、ESPのパリィ自動終了、弱点時間の変更は今回要求しません。
マイコンのファームウェアは現状のまま使います。以下のマイコンの動作・ログ形式は共有資料に基づくもので、実機での確認はこれからです。

## 1. 役割分担

| 担当 | 役割 |
| --- | --- |
| Webアプリ | 難易度選択、画面・HP・60秒の進行、既存コマンドの送信、ESP結果の受信 |
| Pythonアプリ | 会話・BGM・4拍の予告音、音声出力に基づく予定時刻の提供 |
| XIAO ESP32C6 | 既存のUSBシリアル操作、ESP-NOW中継、確定結果のログ出力 |
| M5StickS3 | 既存の通常・予告・有効状態と衝撃検出、パリィ成功判定 |
| AtomS3R | 既存の弱点A・10秒の受付、命中検出・終了通知 |

```text
Pythonアプリ
  ↕ WebSocket
Webアプリ
  ↕ USB（115200bps、改行LF）
XIAO
  ├─ ESP-NOW ↔ M5StickS3（パリィ）
  └─ ESP-NOW ↔ AtomS3R（弱点A）
```

ESPが成功とした結果は、アプリへの到着時刻で判定し直しません。
開始前に難易度を選び、BGMの曲・テンポは1プレイ中固定します。ESP連携では弱点は全難易度で10秒です。
弱点Aは試験用に画面の中央・青へ対応付けています。B/Cは今回の対象外です。別途追加したROSロボット連動では、ESPのパリィ成功をWeb経由でロボットへ通知します。開始・終了を含む手順は[ロボット連携の手順と通信仕様](robot-integration.md)を参照してください。

## 2. 使うコマンドと結果

### アプリ → XIAO

| 指示 | 用途 |
| --- | --- |
| `r` | 開始前・終了・中断時の初期化 |
| `p 0` | パリィ判定を無効に戻す |
| `p 1` | パリィ予告 |
| `p 2` | パリィ有効化 |
| `w A` | 弱点Aを有効化（機器側で10秒を管理） |

難易度コマンド`d 1/2/3`は今回使いません。資料では値の受領・保存までの実装であり、初回は既存の衝撃検出設定を使います。

### XIAO → アプリ

| 資料にあるログ | アプリでの扱い |
| --- | --- |
| `[EVENT] PARRY SUCCESS (once)` | 受け成功として弱点攻撃へ進む |
| `[EVENT] WEAK A SUCCESS (once)` | 弱点Aへの命中としてHPを1減らす |
| `[WEAK A] end state confirmed=1` | 弱点の受付終了。命中通知がなければHPを減らさず次へ進む |

行はLFまたはCRLFで区切ります。生の`1`、結果確認途中のログ、検出機側だけのデバッグログはゲーム入力に使いません。
同じ受け・攻撃で結果を二重反映せず、B/Cの結果は採用しません。現在のファームウェアのログ表記が資料と異なる場合は、アプリ側のパーサーを合わせます。

## 3. 音の予定から、指示を先に送る

資料では、パリィ状態を100ms周期で送り、3回連続受信で確定します。反映まで約200〜300msかかる目安があるため、アプリ側に「指示を早める時間」を設けました。

- 設定範囲：0〜500ms。初期値200msは実測前の仮値です。
- Pythonから受け取った4拍の予定を基準に、予告・有効化・解除を同じ量だけ早く送ります。
- パリィの目標区間は「カン」の前後150ms、合計300msです。
- 設定はゲーム開始前に変更します。値を大きくすると、すべての指示がより早くなります。

例えば反映遅延が200msなら、次の送信を目標にします。

| 指示 | 送信する時刻 | 狙う状態変更 |
| --- | --- | --- |
| `p 1` | 最初の「タン」の200ms前 | 最初の「タン」で予告 |
| `p 2` | 「カン」の350ms前 | 「カン」の150ms前から有効 |
| `p 0` | 「カン」の50ms前 | 「カン」の150ms後に無効 |

これは一定の遅れを補正する方法です。通信・処理のばらつき、音声出力位置の推定誤差までは取り除けません。
送信タイマーが予定から100msを超えて遅れた場合や、音声時刻の同期が途切れた場合は中断します。画面を前面にして試してください。

## 4. 一通りのゲームの流れ

1. USBとPythonへ接続し、難易度と前倒し量を選ぶ。
2. 開始時に`r`・`p 0`を送り、会話・カウントダウンの後に対戦を始める。
3. BGMの2・4・6拍から待ちを抽選し、4拍の予告音を流す。予定に合わせて`p 1 → p 2 → p 0`を送る。
4. パリィ成功通知が来たら成功演出を表示し、`w A`で弱点を開く。
5. 弱点Aへの命中通知でHPを減らす。弱点終了通知では次の受けへ進む。
6. 3命中で勝利、60秒経過または紙風船破損の手動入力で敗北。判定停止・初期化を指示し、感想の会話へ進む。

パリィの結果待ちや弱点受付中は、新しい予告を出しません。Python側にも、ESP連携時だけ期限後の予定を保持し、Webから次の受けの準備通知が来るまで待つ処理を追加しています。
弱点の画面表示が0秒になっても、それだけで失敗とはしません。遅れて届いたESPの命中を受け付けます。ただしゲーム全体の終了・中断後は反映しません。

## 5. 現行仕様のまま試すうえでの制約

- パリィには失敗の最終通知がありません。予定した受付終了から1.2秒待っても成功通知がなければ、「成功通知なし」として次へ進みます。衝撃がなかったのか、通信が欠けたのかは区別できません。
- 弱点の終了状態は命中後にも出ます。終了通知の後に近接した命中通知が来る場合に備え、300ms待ってから次へ進みます。
- `w A`送信から10秒＋1.2秒経っても命中・終了が確認できなければ、通信エラーとして中断します。各待ち時間は試験用の初期値です。
- チャンスID・衝撃時刻がないため、前のチャンスから大幅に遅れて届いた結果を完全には識別できません。
- 初期化・弱点有効化には受領確認がありません。USB書き込み成功だけでは検出機への到達を保証できません。開始前に、資料の手順で各機器の受信・検出を確認してください。
- 切断・中断ではアプリ側の予約と未送信の指示を破棄します。接続が残っていれば`p 0`・`r`を送りますが、切断や無線欠落時には機器へ届かない場合があります。再開前に機器が初期状態か確認します。

## 6. 接続・確認手順

1. マイコン3台を起動し、資料に沿ってMACアドレス・チャンネル・各機器の動作を確認する。
2. WebとPythonをESP連携対応の状態に更新し、Pythonを再起動する。起動方法はREADMEを参照。
3. Webで「会話・BGM連携」を選び、Pythonへ接続する。
4. 入力方法を「ESP連携（既存仕様）」にし、その欄からXIAOへ115200bpsで接続する。同じポートをArduinoのシリアルモニタ等で開いたままにしない。
5. 前倒し量を仮の200msにして開始する。USB接続済みの表示は、各検出機の動作確認済みを意味しない。
6. 一通り遊び、音に合わせて成功するかを確認する。終了・中断後は準備画面の送受信記録で確認する。USBの生ログは管理画面で確認できる。

ログには音の予定時刻、指示の送信要求・USB書き込み完了、確定イベントの受信時刻を残します。「カンから何ms後に成功通知が届いたか」は、衝撃の発生時刻や判定のずれそのものではありません。
音声付き動画などで、音と検出機の有効状態・衝撃を確認し、時刻の異なるPCとESPのログをそのまま引き算しないようにします。

まずは「音に合わせても判定が通らない」「判定は通るが画面の反応が遅い」「衝撃を検出できていない」を分けて記録します。
ほぼ一定のずれなら前倒し量を調整し、それでもばらつきが問題なら、状態確定方法や時刻同期・予約実行をメンバーと相談します。
