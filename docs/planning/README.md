## 形式と更新方法

- 文章の編集元はMarkdown（`.md`）です。版を重ねるときは同じファイルを更新します。
- ラフ図はSVG（`.svg`）です。ブラウザや対応する画像ビューアーで開けます。図は模式図であり、実機の形状、配置、寸法、軌道を指定しません。
- 決まっている内容には「確定」、今回のたたき台には「仮案」、決まっていない内容には「未決」を付けます。
- 来場者向けの説明・画面・音声には、「剣で受けて！」のように行動が分かる言葉を使います。開発用語との対応は企画書に記載します。
- 現在のゲーム案を変更したら、企画書と絵コンテを合わせて更新します。共有用PDFなどは、必要になった段階で書き出します。

## 初版の範囲

会議配布版では、「ロボットとチャンバラできた」という来場者体験と、「受ける → 隙をつくる → 一撃を決める」という進行に内容を絞ります。細かな判定、分岐、ROS連携は `concept.md` と `storyboard.md` に残し、体験方針の合意後に開発要件へ落とします。

原案の「音や光に合わせて受ける → 剣が後退 → 3つの弱点から1つがランダム点灯 → 点灯中の命中で1ダメージ」を基本にします。HP3を削れば勝利、紙風船を割られれば敗北。ダメージごとに3段階で難しくなる構成です。

ロボットは自動で動く方針です。スタッフは説明・見守り・ゲーム全体の管理を担当する案です。後退動作、攻撃機会への切り替え、成立判定や破損検出の具体的な連携は未確認です。実機速度を上げることは前提にせず、初期試作では数歩の移動と点灯時間などを調整します。

剣の認識にはカメラを使う予定と共有されています。「プレイヤーの剣を認識し、それを踏まえてロボットが動く」可能性がありますが、詳細は未確認です。動作に認識結果を使うことと、ゲームの成功を判定することは分けて整理します。ROSで届く情報や成立条件は未決とし、ゲーム側は成功・失敗・判定不可を区別して扱う案にしています。

制作順序は、画面ラフ → 仮ボタンで1プレイ → 人がロボット役を演じる体験確認 → 実機接続です。[画面ラフの起動方法](../../README.md)を参照してください。旧8場面の図 `assets/storyboard-v01.svg` は検討履歴です。
